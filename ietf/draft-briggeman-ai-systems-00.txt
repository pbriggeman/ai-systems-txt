Abstract

   This document defines "ai-systems.txt", a plain-text file that an
   organisation that builds or deploys artificial intelligence (AI)
   systems publishes at a well-known location on its own domain.  The
   file declares, in machine-readable and human-readable form, which AI
   systems the organisation has released, what their measured
   capabilities are, who measured them, under what conditions, and where
   the evidence lives.  Every capability claim carries a provenance tier
   (ATTESTED, MEASURED, or DECLARED); anything absent from a valid,
   unexpired file is UNDECLARED by definition.  The file is signed and
   expiring, so claims are attributable, timestamped, and falsifiable.
   robots.txt tells machines what they may take from a publisher; ai-
   systems.txt is the reverse: it tells anyone what a maker has built,
   in a form designed to be checked rather than believed.

1.  Introduction

   Today, information about what AI systems exist and what they can do
   reaches the public as launch marketing, cropped benchmark
   screenshots, leaks, and social-media claims.  Independent parties
   (for example, Epoch AI, METR, Artificial Analysis, and the Stanford
   AI Index) reconstruct the truth after the fact.  Concretely:



Briggeman                  Expires 10 May 2027                  [Page 2]

Internet-Draft               ai-systems.txt                November 2026


   *  There is no canonical, maker-maintained record of what AI systems
      exist.  The closest registry is a third-party reconstruction.

   *  Capability claims are routinely published without the conditions
      that make them comparable (benchmark version, agent scaffold,
      reasoning effort, tool access, date).

   *  Systems are silently updated, renamed, and retired; yesterday's
      claim attaches to today's different system.

   *  Rumor fills every gap.  A rumored system or score can be neither
      confirmed nor denied against any authoritative artefact, so rumor
      and fact circulate with equal weight.

   This document defines a declaration format that addresses those
   problems at the source.  An ai-systems.txt file is:

   *  A _declaration_: the maker's own signed statement, attributable
      and timestamped.

   *  A _claim index_: every capability claim carries its provenance
      tier (Section 2), so a reader can grade it without further
      research.

   *  A _feed_: monitors can fetch, hash, and diff the file on a
      schedule and report precisely what changed.

   The file is not a trust mechanism by itself: a declaration can be
   wrong or dishonest, and the format's defence is falsifiability
   (Section 14), not faith.  It is not a content-permissions file:
   training consent, crawling rules, and AI usage preferences for a
   publisher's content are the subject of [RFC9309], the IETF aipref
   work, and the existing "ai.txt" proposals [AI-TXT]; this file governs
   claims about a maker's _systems_, and its name was chosen to avoid
   colliding with those proposals.  It is not a model card or system
   card; those remain the right place for long-form discussion, and this
   file links to them.  It is not an agent interface description; agent
   cards describe how to call an agent, while this file describes what a
   system is and can do, including systems with no public interface.

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",

   14 [RFC2119] [RFC8174] when, and only when, they appear in all

   Grammar is given in Augmented Backus-Naur Form (ABNF) [RFC5234].  The
   terms _publisher_ (the organisation making the declaration), _system_
   (an AI system declared in the file), _evaluator_ (the party that
   produced a measurement), and _validator_ (software that checks a file
   per Section 12) are used throughout.

3.  Location and Discovery

   1.  The file MUST be served over HTTPS at "https://<domain>/.well-
       known/ai-systems.txt" (well-known URIs per [RFC8615]).

   2.  A JSON mirror with identical content SHOULD be served at
       "https://<domain>/.well-known/ai-systems.json" (Section 11).

   3.  For compatibility, a maker MAY also serve the file at "/ai-
       systems.txt"; the well-known location takes precedence on any
       conflict.

   4.  A detached signature SHOULD be served at the file URL plus ".sig"
       (Section 10).

   5.  Discovery hints (optional; any one suffices): an HTTP response
       header 'Link: </.well-known/ai-systems.txt>; rel="ai-systems";
       type="text/plain"', or a comment line in the maker's robots.txt:
       "# AI-Systems: https://<domain>/.well-known/ai-systems.txt".

   6.  The file applies to the domain it is served from.  A maker with
       several domains serves one file per domain, or identical files
       whose Canonical field lists each domain's URL.

   7.  Media types: "text/plain; charset=utf-8" for the file;
       "application/json" for the mirror.

4.  File Format

4.1.  General Rules

   *  The file is UTF-8 plain text.  Lines are "Field-Name: value".
      Field names are case-insensitive ASCII; values are case-sensitive
      unless a field definition says otherwise.

   *  Lines beginning with "#" are comments.  Blank lines are ignored.
      Parsers MUST ignore fields they do not recognise (forward
      compatibility) and MUST NOT fail on them.





Briggeman                  Expires 10 May 2027                  [Page 5]

Internet-Draft               ai-systems.txt                November 2026


   *  The file has two parts: one header block (fields before the first
      "System" line), then one stanza per system.  A stanza continues
      until the next "System" line or end of file.

   *  An evaluation block begins with an "Evaluation:" line inside a
      stanza; the evaluation-scoped fields that follow belong to it
      until the next "Evaluation:" line or a non-evaluation field.

   *  Repeatable fields MAY appear multiple times; the order of
      "Contact" and "Registry-ID" lines denotes preference and
      canonical-first, respectively.

4.2.  Dates and Numbers

   Dates are YYYY-MM-DD.  Timestamps (Expires) are RFC 3339 [RFC3339]
   timestamps.  Quantities SHOULD be given in plain scientific or
   decimal notation parseable by machines (for example, "4.05e11",
   "2.0e25").  Human suffixes ("405B") are permitted in the text file,
   but the JSON mirror MUST use plain numbers.

4.3.  ABNF (Informative Summary)

   file        = header *( stanza )
   header      = *( field-line / comment / blank )
   stanza      = system-line *( field-line / eval-block /
                               comment / blank )
   system-line = "System:" SP value CRLF
   eval-block  = eval-line *( eval-field )
   eval-line   = "Evaluation:" SP value CRLF
   eval-field  = ("Evaluator" / "Score" / "Conditions" / "Measured" /
                  "Evidence" / "Attestation" / "Tier") ":" SP value CRLF
   field-line  = field-name ":" SP value CRLF
   comment     = "#" *( VCHAR ) CRLF

8.  The Undisclosed Rule

   For Parameters and Training-Compute (and, by extension, any field a
   future version makes required-but-optional-to-answer), a publisher
   MUST either give a value or write "Undisclosed".  Omitting the field
   makes the file invalid.  Rationale: silence is ambiguous (forgotten?
   withheld? not applicable?); an explicit "Undisclosed" is a countable,
   comparable fact - it is what transparency indexes currently have to
   excavate by hand.

9.  Freshness, Versioning, and Change

   *  A file is current until its Expires timestamp; after that,
      validators MUST label every claim in it STALE.

   *  Publishers SHOULD update the file in the same release process as
      the system itself; a system that is served but absent from a
      current file is, for consumers of this specification, UNDECLARED.

   *  Each published version SHOULD remain fetchable (via Previous-
      Version chains or dated URLs) so diffs are auditable.  A monitor's
      diff of two versions - systems added or removed, scores changed,
      fields edited - is the authoritative answer to "what changed and
      when", ending the "quietly updated model" class of rumor.

10.  Signing

   *  The file MUST name a detached signature (the Signature header)
      covering the exact bytes of the file as served.  OpenPGP (as in
      [RFC9116] practice) or JWS are both acceptable; the signature
      file's format is self-describing.

   *  Validators MUST report one of: signature-verified, signature-
      present-unverified, signature-missing, or signature-invalid.  Only
      signature-verified supports treating the file as authentically the
      publisher's.

   *  Signatures cover the served bytes; publishers MUST NOT rely on
      whitespace-insensitive verification.

11.  JSON Mirror

   The JSON mirror carries identical content for machine consumers.
   Field names are lower-snake-case; quantities are numbers; dates are
   strings as in Section 4.2.  An abridged JSON Schema (draft 2020-12)
   for the mirror is given in Appendix B.  On any conflict between the
   text file and the mirror, the signed text file wins.

12.  Validator Behaviour

   A conforming validator, given a file (path or URL), MUST be able to:

   1.  _Authenticate_: fetch over HTTPS; check Canonical against the
       fetch URL; check the signature state (Section 10).

   2.  _Check freshness_: parse Expires; label the file current or
       STALE.

   3.  _Lint_: required header and stanza fields present; required-but-
       optional fields explicitly valued or "Undisclosed"; Status in
       vocabulary; dates parse; every evaluation block complete for its
       stated tier; tiers recomputed and downgraded where unsupported.

   4.  _Cross-check_: for each system, look up the reference registry
       (the Epoch AI models dataset [EPOCH] is the reference registry
       for this draft) and report IN-REGISTRY, NOT-IN-REGISTRY, or
       CONTRADICTED.  For each MEASURED or ATTESTED claim, compare
       against the evaluator's published data where a machine-readable
       source exists, and verify the Evidence URL resolves.

   5.  _Rumor sweep_: given a list of names circulating publicly, report
       each as declared in the file, or as "UNDECLARED - rumor tier" if
       absent.  Validators MUST NOT import rumored systems into the
       declared set.

   6.  _Diff_: given a previous version, report added and removed
       systems and every changed field and score.

   7.  _Report_: emit a machine-readable report (JSON) containing, per
       system and per claim, its tier or verdict, all errors and
       warnings, and the file's SHA-256 hash.  Human-readable renderings
       SHOULD be offered.  Verdict vocabulary: VALID, VALID-WITH-
       WARNINGS, INVALID, plus per-claim ATTESTED / MEASURED / DECLARED
       / CONTRADICTED / STALE / EVIDENCE-UNREACHABLE and per-system
       registry verdicts as in item 4.

12.1.  Comparison Tolerances

   Exact equality is too strict for reconstructed registries.  Reference
   tolerances: release dates differing by at most 31 days are a warning,
   not a contradiction; parameter counts differing by more than a factor
   of 2, and training compute differing by more than a factor of 3
   (registries estimate compute), are contradictions.  An evaluator's
   own republication of a score supersedes the file's transcription of
   it.

13.  Conformance Levels

   Publisher levels:

   Level 1 - Declared  Valid file, all required fields, signature named.

   Level 2 - Measured  At least one MEASURED evaluation per generally-
      available system, JSON mirror published, Registry-ID values cross-
      linked.

   Level 3 - Attested  ATTESTED evaluations from at least one
      independent evaluator for frontier systems, Previous-Version chain
      maintained, expiry of 90 days or less.

   Validator conformance: implements all of Section 12 and publishes its
   test results against the reference test suite (valid, expired,
   broken, contradicted, and rumor cases).

14.  Security Considerations

   *  _Dishonest declarations._ The format cannot prevent lying.  It
      converts lies from deniable rumors into signed, timestamped,
      hashed statements that independent evaluators can contradict on
      the record - permanently attributable.  That is the same bargain
      that makes [RFC9116] files and financial filings useful.

   *  _Spoofed files._ Files on lookalike domains are not the
      publisher's.  Canonical checking plus signature verification are
      the defence; consumers MUST NOT trust an unsigned or canonical-
      mismatched file.

   *  _Stale mirrors and caches._ Expires bounds the damage; validators
      MUST surface staleness rather than silently serving old claims.

   *  _Benchmark gaming._ Mandatory Conditions and versioned benchmarks
      make selective reporting visible: a publisher that reports only
      flattering benchmarks will show conspicuously fewer evaluation
      blocks than its peers - itself a signal.

   *  _Signature stripping and downgrade._ A mirror that drops the
      signature reduces every claim to at most DECLARED; validators MUST
      reflect that.

   *  _Denial by omission._ A publisher can omit a secret system.  The
      file makes that omission visible as a state (UNDECLARED) once the
      system is rumored, rather than leaving the rumor unanswerable
      either way.

15.  Privacy Considerations

   The file contains only public, organisational information.  Personal
   data SHOULD NOT appear beyond role-based contacts (as in [RFC9116]
   practice).  Nothing in this specification requires disclosing trade
   secrets: the Undisclosed rule exists precisely so a publisher can be
   complete about the shape of its disclosure without revealing
   protected values.

16.  Adoption and Relationship to Existing Work

   Adoption proceeds in layers: makers publish Level 1 files (cost: one
   static file in the release checklist); evaluators publish results in
   linkable, hashable reports so blocks can be ATTESTED, and may
   countersign; registries and monitors ingest files as a first-party
   source; buyers and journalists cite tiers rather than screenshots.

   *  [RFC9309] (robots.txt): the directional opposite and the adoption
      template - voluntary, trivial, publisher-served.

   *  [RFC9116] (security.txt): the structural template - well-known
      location, "Field: value" lines, required Contact and Expires,
      signed files, an IANA field registry.

   *  "ai.txt" proposals [AI-TXT]: content permissions for publishers;
      complementary, and the reason for this file's distinct name.

   *  llms.txt: a content index for agents; unrelated purpose.

   *  Model cards and system cards: long-form companions; linked, not
      replaced.

   *  Agent cards (A2A) and MCP server cards: runtime interface
      descriptions; a complementary layer.

   *  Epoch AI, METR, Artificial Analysis, and the Stanford AI Index:
      the independent reconstruction layer this file feeds and is
      checked against; adoption of this specification makes their work
      faster, not obsolete.
